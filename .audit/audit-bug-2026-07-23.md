## P1

### F1 — Settings menu toggled open-then-closed by the hardware's double-fire of DOUBLE_CLICK_EVENT (no per-event-type debounce)

**src/main.ts:696** | verification: 3/3 non-refuted | corroboration: none (input-concurrency lens)

[EXTERNAL-VALIDATION: hardware] The G2 appendix states the SDK fires DOUBLE_CLICK_EVENT twice (~110ms apart) per physical double-tap, and instructs debouncing per event type. handleBridgeEvent has NO debounce on the double-click path (lines 696-701). Because menu.open()/menu.close() are pure state toggles keyed on menu.isOpen(), the two events cancel: from a game (coin/dice) view the FIRST event runs menu.open() and the SECOND (~110ms later, still no debounce) sees menu.isOpen()===true and runs menu.close(). Net effect of one physical double-tap = the settings menu opens and immediately closes, so it is effectively unreachable via its documented gesture. Same root cause produces two more symmetric misbehaviors: (a) double-tapping to CLOSE the menu (menu.close() then menu.open()) reopens it; (b) from the home screen the two events fire shutDownPageContainer(1) twice. The settings menu is the only route to Home/Background/Tally/Reset/Exit from a mode view, so this is a dead-but-alive reliability hole on the primary control surface. Also note menuTakeover (onOpen) calls flip/roll.clearResult(), so the transient open also wipes a showing result's status when it flickers. Fix requires a per-DOUBLE_CLICK_EVENT debounce (swallow the second event within ~200ms) so one physical double-tap maps to one logical toggle. The debounce must NOT be global (single-click/swipe must still pass), matching the appendix's 'debounce per event type, not globally.' Distinct root cause from F10 (which is about the busy-gate suppressing the open branch during an animation), though both live in this handler.

**Repro:** On glasses, from the coin-flip or dice view (menu closed, home closed, no animation in flight), physically double-tap the temple. First DOUBLE_CLICK_EVENT runs menu.open(); the SDK's second DOUBLE_CLICK_EVENT ~110ms later runs menu.close(). The settings menu flashes and closes; repeating never leaves it open. Conversely, when the menu is open, one double-tap runs close() then open(), reopening it.

### F2 — createStartUpPageContainer non-zero result has no rebuildPageContainer fallback — dead-but-alive session

**src/main.ts:167** | verification: 3/3 non-refuted | corroboration: none (resilience-failsoft lens)

[EXTERNAL-VALIDATION: hardware] The G2 appendix states createStartUpPageContainer is one-shot per session: a second call (WebView reload / HMR / session re-entry without a clean teardown) returns code 1 silently and the bridge never initializes — the app renders the cached frame but is fully unresponsive, and the documented mitigation is a rebuildPageContainer fallback on any non-zero create result. Here the only handling of createResult !== 0 is console.error (main.ts:167-169); execution then continues unconditionally: onEvenHubEvent subscribes and home.open() runs. But home.open()->homeTakeover->switchPage('home') is a guaranteed no-op because currentPageKind is already 'home' (main.ts:134,153-161), so rebuildPageContainer is NEVER invoked. There is no recovery path — the session stays wedged (renders a stale frame, gestures do nothing) until the user force-relaunches. Every other init assumption (that the page container exists) is now false, so all subsequent textContainerUpgrade/updateImageRawData writes also no-op. Distinct from F17 (the runtime page-swap rebuild-result discard): this is the create-path lacking any fallback at all.

**Repro:** Trigger any path that re-runs the module against an already-initialized SDK session (Even WebView reload, dev HMR, or app re-entry that resumes rather than tears down the WebView). createStartUpPageContainer returns 1; the code logs and proceeds; the app shows the previous frame and ignores all taps/swipes with no self-recovery.

### F3 — Mode switch from phone mid-animation isn't guarded by isBusy — old mode's result paints over the new mode's view (two-writer race on shared containers)

**src/main.ts:355** | verification: 3/3 non-refuted | corroboration: found independently by state-machine and input-concurrency lenses

setDiceMode() (line 355) and applyMode() (line 337) have no isBusy guard, unlike devRoll() which explicitly checks `roll.isBusy() || flip.isBusy()` (line 617). applyMode only clears both controllers' resultShowing via clearResult(); it does NOT stop an in-flight flip/roll animation. The animation's async loop (runFlip/runRoll) keeps running: setDiceMode synchronously repaints the new mode's idle image + idle status, but the still-running old-mode loop then enqueues its remaining frames AFTER those writes to the same shared containers (IDS.coinImage / IDS.statusBar). Because bridgeQueue serializes strictly in enqueue order, the old animation's final frame wins — onResult() + setStatus(HEADS/ROLLED N) + sendImage(result face) land last. Net result: after switching coin->dice mid-flip, the glasses/preview end up showing the coin's HEADS image and 'HEADS' status while diceMode is now true; the coin frame is painted over the die image container. The onResult also increments the OLD mode's tally while the NEW mode's tally is displayed. The stale display persists until the next swipe-up. resultShowing is also left true on the now-inactive controller (only cleared on the next switch). Data is not corrupted, but the display is a false/misleading result for a mode the user is no longer in. Symmetric in both directions (dice->coin mid-roll shows a die face + 'ROLLED N' in coin mode). Only reachable from the phone mode-select: on-glasses the mode is chosen from the home screen, and reaching home requires a double-tap swallowed while busy (line 699).

**Repro:** 1) On the phone, ensure Coin mode. 2) On the glasses, swipe up to start a coin flip (busy=true). 3) While the tumble animation is still running, on the phone change the Mode dropdown to 'Dice Roll'. 4) The view switches to the die idle face/roll status, then the still-running flip repaints the coin's HEADS/TAILS image and status on top, so the glasses show a coin result while in dice mode until the next swipe-up.

## P3

### F5 — Startup asset load has no error boundary — a single coin-frame fetch/decode failure kills the entire app

**src/main.ts:96** | verification: 1/1 non-refuted | corroboration: none (resilience-failsoft lens)

The top-level module init is an unguarded await chain (main.ts:95-118): waitForEvenAppBridge, then loadCoinAssets (a Promise.all over all six coin frames, assets.ts:138-153), then the kv loads. loadCoinAssets rejects if any single frame's fetchPng fails (!res.ok or non-PNG magic bytes, assets.ts:90-103) or renderProcessed throws (2D context unavailable, assets.ts:54). Because there is no try/catch anywhere around startup, one such rejection aborts the whole init BEFORE createStartUpPageContainer (main.ts:163), before onEvenHubEvent subscription (main.ts:732), and before home.open() (main.ts:735). Result: a totally dead black app — no page, no input handler, no fail-soft message — recoverable only by relaunch. Assets are local to the WebView so reachability is low, but the blast radius is total app death from any one transient asset hiccup or a corrupt/undecodable bundled PNG.

**Repro:** First run with an empty kv cache while the WebView asset server drops or mis-serves one of /coin/*.png (or ships a byte-corrupt PNG that fails img.decode / UPNG.encode): loadCoinAssets' Promise.all rejects, module init throws, and nothing is ever rendered or wired — the app is dead until reinstall/relaunch.

### F6 — Rejected-promise memoization poisons the dice asset cache — one transient failure permanently breaks a die face for the session

**src/dice.ts:68** | verification: 1/1 non-refuted | corroboration: none (resilience-failsoft lens)

Both dice-asset caches store the PROMISE, not the resolved value, and never evict on rejection. imageAt (dice.ts:66-73) does decodedImages.set(path, fetchPng(path).then(decodePng)); processed() (dice.ts:103-123) does memo.set(key, p) where p wraps the fetch+renderProcessed. If a fetch/decode transiently fails, the rejected promise is cached forever for that session. Every later roll that lands on the same value/pose re-awaits the poisoned promise in roll.ts (await stepPromises[i] / await settlePromise / await facePromise, roll.ts:189-201), which re-throws; runRoll rejects and is swallowed by trigger's .catch (roll.ts:213-216), so the roll silently aborts mid-animation with no result recorded and no error shown. The die is now permanently unable to display that face/pose until app relaunch — a transient blip becomes a persistent, self-inflicted dead feature. STATE-PROVENANCE: the only writer to decodedImages/memo sets a promise unconditionally on first miss and there is no path that clears a rejected entry, so the reader (roll.ts) is stranded.

**Repro:** In dice mode, roll while the WebView momentarily fails to serve /dice/d6-iso-N.png (or that decode throws once). That roll aborts. For the rest of the session, every roll whose tumble/settle/result hits the poisoned value+pose aborts partway with no result and no message, even after the underlying fetch would now succeed; only relaunch clears it.

### F7 — Slow BLE link (>5s per call) aborts flip/roll mid-animation and emits unhandled rejections at every void-enqueue site

**src/bridgeQueue.ts:37** | verification: 1/1 non-refuted | corroboration: none (resilience-failsoft lens)

enqueue rejects the CALLER at DEFAULT_TIMEOUT_MS=5000 (bridgeQueue.ts:37-39) while intentionally leaving the real call in flight. Two resilience consequences under a slow-but-alive BLE link (>5s/call): (1) flip.ts and roll.ts await sendImage/setStatus (flip.ts:130-133, roll.ts:181-201); a 5s timeout throws mid-animation, caught by trigger's .catch which sets busy=false but leaves resultShowing=false and never runs onResult — the flip/roll is silently dropped with no count recorded (recoverable by swiping again, but the abandoned frames later paint stale coin/status content when the real calls eventually settle behind the queue). (2) Every fire-and-forget 'void enqueue(...)' site (drizzle main.ts:215/256/305/469/479, menu render menu.ts:109, kvSet kv.ts:43, repaint main.ts:325) becomes an unhandled promise rejection on that 5s timeout, plus the sendDrizzleFrame().finally() chain (main.ts:215-217) rethrows into a void. Not fatal, but a stalled link produces a steady stream of unhandled rejections and silently-lost flips/rolls. (Related to but distinct from F4, which is the specific drizzle-guard ineffectiveness defect enabled by this same 5s timeout mechanism.)

**Repro:** With BLE degraded so each bridge write takes >5s, swipe up to flip: the first frame's await times out at 5s, runFlip throws, busy resets, no result is recorded or shown; concurrently the drizzle/status/tally void-enqueue calls reject unhandled. When the link recovers, the abandoned frames render late as phantom updates.

### F8 — HARD_SETTLE_CAP advances the queue while a slow-but-alive BLE call is still on the wire — the concurrent-call collision the queue exists to prevent

**src/bridgeQueue.ts:63** | verification: 1/1 non-refuted | corroboration: found independently by resilience-failsoft and input-concurrency lenses

[EXTERNAL-VALIDATION: hardware] The queue's stated invariant (bridgeQueue.ts:1-13) is that the SDK must never see two BLE calls in flight at once because concurrent calls crash the G2 connection into a frozen app needing relaunch. The chain normally advances only when the real call settles — but HARD_SETTLE_CAP_MS=12000 (bridgeQueue.ts:63) unconditionally advances via advance() after 12s even if the real call is still pending, then starts the next queued call while the previous BLE send may still be on the wire. On a link that stalls past 12s and then RECOVERS (as opposed to being truly dead), this fires exactly the concurrent-send collision the queue is built to avoid: the original send's real promise settles after the cap already dispatched the next call. The comment frames 12s as a last-resort anti-wedge given ~0.5-2s real latency, so this is an accepted tradeoff, but it is a real reachable failure mode on a slow-recover link, and it is the one path where the serializing seam is deliberately broken. The fixer should weigh whether the next call should be gated on real-settle-or-hard-abort rather than a timer that fires while the original may still be pending.

**Repro:** A bridge write stalls (BLE congestion / temporary link loss) past 12s without erroring; the hard cap advances the chain and dispatches the next updateImageRawData/textContainerUpgrade; the original send then completes late, putting two calls on the G2 wire simultaneously and risking the connection-crash / frozen-app state.

### F9 — Phone-driven setting/mode changes don't re-render an open on-glasses settings menu, so its rows show stale values (and the next tap toggles from the wrong state)

**src/main.ts:407** | verification: 1/1 non-refuted | corroboration: none (state-machine lens)

### F10 — During a flip/roll animation, double-tap is fully consumed with no menu-open and no exit path

**src/main.ts:696** | verification: 1/1 non-refuted | corroboration: none (state-machine lens)

[EXTERNAL-VALIDATION: hardware] The double-tap handler (lines 696-701) routes: home open -> shutDownPageContainer(1); menu open -> menu.close(); else `if (!surface.isBusy()) menu.open()`. **Repro:** 1) Swipe up to start a flip/roll (busy=true). 2) During the tumble animation, double-tap. 3) Nothing happens (no settings menu, no exit prompt) until the animation finishes and busy clears.

### F13 — kvGet SDK back-fill is a read-then-write across an await with no same-key serialization — a concurrent kvSet clobbers the authoritative store with a stale value

**src/kv.ts:29** | verification: 1/1 non-refuted | corroboration: none (storage-sync lens)

In kvGet, when localStorage misses (line 13-14 falsy) the code awaits the SDK-store read through the bridge queue (line 22), then unconditionally back-fills localStorage with the SDK value (line 29) and returns it. That is a read (localStorage miss) -> await -> write (localStorage) sequence with no guard that localStorage is still absent when the write lands. localStorage is the AUTHORITATIVE store per the module contract (lines 4-10). If any kvSet(sameKey, newValue) executes during the SDK-get suspension, it synchronously writes localStorage=newValue; when kvGet resumes it overwrites that with the older SDK value AND returns the stale value to its caller — an authoritative-store corruption plus a stale read. Latent today: no current caller overlaps a get and a set on the same key (startup loads at main.ts:96-110 are sequentially awaited; cache get/set for a given key are chained inside the memoized processed()/map callbacks in dice.ts:110-120 and assets.ts:141-149, never concurrent). But kv.ts is a generic reusable seam with no serialization of same-key access, so correctness relies entirely on callers never overlapping — an invariant nothing enforces.

**Repro:** Latent (no reachable trigger in the current call graph). Would fire if two same-key accesses overlap, e.g. a future caller does kvGet('tally') (localStorage empty, awaiting the SDK read) while a flip result's saveTally('tally', {heads:1,tails:0}) runs in the same window: the flip's localStorage write is then clobbered by kvGet's back-fill of the older SDK value, and kvGet returns the stale tally.

### F14 — Dual-store divergence silently resurrects stale tallies/settings after a localStorage eviction whose matching SDK write was dropped

**src/kv.ts:43** | verification: 1/1 non-refuted | corroboration: none (storage-sync lens)

[EXTERNAL-VALIDATION: hardware] kvSet writes localStorage synchronously (authoritative) and enqueues a best-effort SDK-store write (line 43); the SDK write is fire-and-forget (void enqueue) and, per the module comment (lines 4-10), is 'observed to silently drop writes' on iOS WKWebView. kvGet prefers localStorage and only falls back to the SDK store (lines 13-22). So if a write (e.g. resetTally at main.ts:444-455, or a tally increment, or a settings toggle) lands in localStorage but its SDK copy is dropped, the two stores diverge with localStorage holding the newer value. iOS WKWebView is known to evict localStorage under storage pressure / 7-day inactivity. After such an eviction, kvGet reads the STALE SDK value and back-fills localStorage with it — the reset (or the last N flips) is silently undone and re-persisted as authoritative. This is the acknowledged tradeoff of the localStorage-authoritative design (it can't defend against localStorage eviction with any best-effort second store), so it may be judged by-design; flagged because the failure is silent user-visible data loss on a reachable-in-principle path and can only be confirmed on hardware.

**Repro:** On iOS glasses: user resets the tally (double-tap -> settings -> Reset current tally; writes localStorage {0,0} and enqueues an SDK write that the SDK silently drops so the SDK store keeps the old non-zero value). App stays unused >7 days (or the OS evicts WKWebView localStorage). Next launch: loadTally -> kvGet('tally') misses localStorage, reads the stale non-zero value from the SDK store, back-fills localStorage with it. The reset is gone and the old counts reappear as authoritative.

### F16 — keepAlive re-activates on every gesture (leaking a Web Lock per tap) when AudioContext is unavailable

**Repro:** Run in an environment where window.AudioContext and window.webkitAudioContext are both undefined (or the ctor throws) but navigator.locks exists. After N gestures there are N pending lock requests that never drain.
